# Визуальная спецификация диаграмм SlideCraft для PowerPoint

> Дата: 24 октября 2026; обновлено 25 октября · Статус: реализованы синтетические примеры, просмотрены светлые и тёмные HTML-рендеры; Office-проверка не завершена · [Research](diagram-design-review-2026-10.md) · [План реализации](diagram-design-adoption-plan-2026-10.md) · [Фактическая реализация и ограничения](diagram-design-implementation-2026-10.md).

## Как должны выглядеть диаграммы

Цель — спокойные, выразительные деловые слайды: читаемый заголовок с выводом, крупная диаграмма, один очевидный фокус, короткие подписи и достаточно свободного места. Внешний вид должен соответствовать остальной презентации и выдерживать ручную правку в PowerPoint.

От upstream берём визуальную иерархию, аккуратные соединения, прямые подписи и сдержанное выделение главного. Конкретные шрифты, фон, размеры и обрамление берём из темы SlideCraft. Подробное сопоставление источников — в [review](diagram-design-review-2026-10.md).

Основное направление первого выпуска — существующая **Consulting Classic**: белый фон, тёмные подписи, один синий акцент. **Editorial Fintech** проверяет совместимость с более выраженным оформлением страницы; **Midnight** — читаемость на тёмном фоне. Это темы одного layout, а не три независимые реализации диаграммы. [Темы](../../library/themes/consulting-classic.json) · [Editorial Fintech](../../library/themes/editorial-fintech.json) · [Midnight](../../library/themes/midnight.json).

## Композиция слайда и читаемость

Числа ниже — стартовые ориентиры для проектирования и проверки, не универсальные нормативы. Реализованы режимы `readability: report` (шрифты темы) и `present` (повышенные минимальные размеры). Точные правила — в [руководстве](../how-to/create-diagrams.md). Итог зависит от темы, длины текста, режима использования и фактического рендера.

| Решение | Для чтения отчёта / PDF | Для показа на экране |
|---|---|---|
| Заголовок | Размер темы, обычно 24–26 pt; до двух строк | Ориентир 28–32 pt, короткая формулировка |
| Основные подписи внутри диаграммы | Ориентир 14–16 pt | Ориентир 18–20 pt |
| Второстепенные пояснения | Ориентир 11–12 pt, без ключевого вывода мелким шрифтом | Ориентир 14–16 pt; всё, что аудитория обязана прочесть, переводить в основную подпись |
| Плотность | Допустимы значения, единицы и короткие пояснения рядом | Меньше узлов и рядов; подробности — следующим слайдом |
| Источники | Штатный source frame | Штатный source frame; важная оговорка также видна в основном содержании |
| Переполнение | Переписать подпись, изменить композицию или разделить слайд | Сначала сократить объём с сохранением смысла; автоматическое уменьшение не должно нарушать выбранный порог читаемости |

Сейчас Consulting Classic и Editorial Fintech имеют `body: 14`, Midnight — `body: 15`. Новые ориентиры для показа нужно выразить через согласованную настройку типографики и вместимости, используя назначение из brief. Их нельзя вводить локальным увеличением шрифта только в одной диаграмме. Отдельный публичный API для такой настройки этим документом не утверждается.

Диаграмма размещается внутри `ctx.body` после резервирования title, source и takeaway. Используем формат 16:9 и общую сетку SlideCraft. Не переносим `viewBox` upstream вместе с его веб-заголовком, легендой и footer внутрь слайда: страница уже имеет собственное обрамление. [Формат](../../src/engine/format.ts) · [Архитектура композиции](../explanation/architecture.md).

Две базовые композиции:

- **Диаграмма на ширину body:** architecture delta, Sankey, journey, blueprint и схемы с длинными подписями. Вывод несёт action title; дополнительная полоса вывода используется, только если добавляет смысл.
- **Диаграмма с пояснением сбоку:** heatmap, treemap, dumbbell и другие аналитические exhibits. Начальный ориентир — около двух третей ширины под данные и одной трети под короткое объяснение; пропорция уступает измеренной читаемости. Для `chart-takeaway` уже есть подобная структура.

## Общий визуальный язык

| Элемент | Решение для SlideCraft | Что проверять |
|---|---|---|
| Фон | `background`; области группировки — `surface` | Нет декоративной сетки, текстуры или градиента, мешающих данным |
| Цвет | `ink` и `muted` для контекста, `accent` для вывода | Внимание сначала попадает на предмет заголовка; категории и статусы остаются различимы без цвета |
| Шкала величины | Последовательная шкала для unsigned data; diverging только при содержательном центре | Цветовая шкала не превращается в случайную палитру; focal styling не скрывает значение |
| Контуры | Начальный ориентир 0,75–1,25 pt, фокус 1,5–2 pt | Линии читаются при показе, не становятся тяжелее текста и данных |
| Блоки | Лёгкая заливка или контур; начальный радиус 0,04–0,08 in | Форма различает роль, а не добавляет оформление каждому объекту |
| Интервалы | Повторяемые отступы; ориентир 0,25–0,4 in между крупными группами | Группы читаются через пространство; подписи и коннекторы имеют отдельные места |
| Подписи | Непосредственно у объекта, единицы у шкалы/значения, одинаковое выравнивание | Легенда нужна только там, где прямое подписывание не решает задачу |
| Соединения | Обычно ортогональные, с устойчивыми ports и зазорами | Понятно, откуда и куда идёт линия; data curves и fishbone bones сохраняют свою геометрию |
| Иконки | Только если различают роли; единый стиль и масштаб | Не заменяют обязательные подписи и не добавляются ради заполнения места |
| Эффекты | Простые заливки, линии и editable geometry | Смысл и иерархия сохраняются без теней, свечения, фильтров и анимации |

Эти параметры следует выразить в общих helpers/токенах после прототипирования. Не фиксировать локальные цвета и шрифты в каждом layout. Фокус может включать несколько сегментов одного пути или несколько одинаково значимых объектов; ограничение цвета не должно искажать данные.

## Визуальный рецепт для каждого приоритетного типа

| Тип | Как делаем привлекательным и понятным | Защита от неудачного результата |
|---|---|---|
| **Heatmap** | Ровные cells, короткие labels по краям, спокойная тональная шкала; нужную область выделяем контуром и подписью | Не обводим каждую ячейку тяжёлой рамкой; N/A отличается от нуля; хронологические колонки не переставляем ради картинки |
| **Dumbbell** | По одной категории на строку; тонкая связь, полая точка «до» и заполненная «после»; выделена важная строка | Обе точки читаются при равных значениях; знак изменения написан явно, если нужен; форма сохраняет смысл при печати без цвета |
| **Slopegraph** | Две вертикальные оси, значения и названия непосредственно у концов; достаточно места в боковых полях; один главный ряд выделен толщиной | Разводим конфликтующие подписи с leader lines, не сдвигая data points; пересечения показывают реальные изменения порядка |
| **Fishbone** | Тонкий позвоночник, короткие категории, наблюдаемый эффект в компактном блоке справа; причины аккуратно выровнены | Для показа начинаем с 4 категорий и 1–2 причин в каждой; подробный разбор — отдельным слайдом; выделение гипотезы сопровождается её статусом |
| **Treemap** | Крупные чистые площади, небольшой одинаковый промежуток, подписи в одной позиции внутри cells; имя и значение образуют ясную иерархию | Площади сохраняют доли после gutters; мелким элементам даём внешнее пояснение, не увеличивая их размер и не поворачивая текст |
| **Architecture delta** | Две схемы одинаковой ширины с одинаковыми позициями сохранённых nodes; изменения имеют текстовый знак; краткий ledger рядом или ниже | Центральный ledger допускаем только при читаемых схемах; если весь список не помещается, добавляем detail slide с полным перечнем, а не скрываем изменения |
| **Swimlane** | Сдержанные горизонтальные полосы, имена ролей слева, шаги на общей сетке; главное — читаемый handoff | Не красим каждую роль ярким цветом; возвратам выделяем трассу; стрелки не проходят через подписи других lanes |
| **Sankey** | Три ясно подписанных этапа, плавные полупрозрачные ribbons, один выделенный поток, значения у nodes | Размеры потоков вычисляются из данных; подписи среднего этапа стоят в свободных промежутках; маленькие значения не раздуваются для красоты |
| **Loop / flywheel** | Несколько крупных шагов по кольцу, свободный центр для накопленного результата, ясное замыкание | Нет повторяющихся декоративных стрелок; подписи горизонтальны; hub появляется только при соответствующем смысле |
| **Layer stack** | Спокойные горизонтальные уровни, одинаковое выравнивание подписей, выделен обсуждаемый уровень | Толщина слоя не выдаётся за количественную меру; стрелка зависимости не появляется без такого отношения в данных |
| **Journey** | Общие колонки этапов, короткие actions/touchpoints, простая sentiment line и явно подписанная проблема | Sentiment имеет источник или статус hypothesis; кривая не сглаживается так, чтобы возникали отсутствующие наблюдения |
| **Service blueprint** | Единая stage grid, ясная граница видимости, backstage слегка отделён заливкой, один проблемный cell в фокусе | Строки получают место по тексту; не вмещаем пять плотных таблиц микрошрифтом; обязательные layers и N/A остаются понятны |
| **Flowchart / state** | Небольшое число различимых форм, короткие подписи переходов, ясные входы и выходы | Различаем решение и состояние; цикл не похож на случайно пересекшуюся стрелку; legend объясняет только действительно использованные символы |
| **Sequence** | Ровные вертикальные lifelines, последовательный ритм messages, минимум декоративных participant boxes | События читаются сверху вниз; fragments не перекрывают текст; длинный сценарий разбивается с сохранением порядка |

Это проектные решения SlideCraft, а не описание уже готовой галереи. Рецепты остаются зависимыми от содержимого: приятная композиция не оправдывает удаление данных, подмену шкалы или неявное объединение категорий.

## Что требуется именно от PowerPoint

1. **Редактирование.** Текст, блоки, значения и связи доступны как соответствующие native objects или editable freeforms. У количественных shapes нет обещания встроенной chart data sheet; этот уровень поддержки обозначается отдельно.
2. **Удобная ручная правка.** Объекты получают понятные имена. Логическая группировка полезна, если сохраняет доступ к подписям и поддерживается общим exporter; её нужно проверить отдельно. Автоматическое движение связанных стрелок вместе с узлом не обещается без OOXML connections.
3. **Типографика.** Используются fonts темы и штатные измерения. Проверяются длинные RU/EN labels, знаки процентов, минусы, переносы и подмена шрифта на целевой машине.
4. **Предсказуемый внешний вид.** Проверяются native curves, opacity, стрелки, порядок перекрытий и исчезновение мелких линий. Хороший SVG preview не заменяет просмотр экспортированного PPTX.
5. **Целостный слайд.** Цвета и рамка совпадают с остальным deck; диаграмма не содержит второй вложенной «страницы» с собственным заголовком и footer.

## Как проверять, что получилось красиво

До масштабирования библиотеки нужен небольшой **набор визуальных эталонов**. Это будущая работа по реализации, а не результат текущего research.

- [ ] Для каждого типа первой очереди подготовить одинаковые данные в двух кандидатах композиции; выбрать более читаемый вариант и записать причину. Это сравнение дизайна, не необходимость нового обязательного пользовательского checkpoint.
- [ ] Построить выбранный вариант в Consulting Classic и Midnight; Editorial Fintech проверить как пример насыщенного frame. Остальные темы проходят общий harness.
- [ ] Проверить короткий и предельно допустимый текст, нормальный и плотный набор данных, RU/EN. Плотный случай обязан корректно уместиться или дать полезную диагностику.
- [ ] Просмотреть actual PowerPoint в режиме показа: сначала без увеличения найти главный вывод, затем прочитать обязательные подписи. Контактный лист нужен для ритма и различимости exhibits; чтение деталей проверяется на отдельном слайде.
- [ ] Изменить подпись, цвет и положение одного объекта в PowerPoint; убедиться, что редактируемость практически полезна. Сохранённый файл заново открыть и просмотреть.
- [ ] Выполнить штатный visual QA HTML ↔ Office; записать обнаруженные расхождения и отдельно дизайнерские замечания.

| Критерий | Условие приёмки |
|---|---|
| Иерархия | Предмет заголовка находится сразу; остальные элементы дают контекст |
| Читаемость | Все обязательные подписи читаются в выбранном режиме без увеличения |
| Композиция | Диаграмма использует body осмысленно; нет тесных углов и случайных пустот |
| Аккуратность | Повторяемые отступы, ровные подписи, понятные endpoints, отсутствие ненужных рамок |
| Достоверность | Акцент, сортировка, размер и цвет не изменяют смысл исходных данных |
| Согласованность | Диаграмма выглядит частью этой презентации во всех проверенных темах |
| PowerPoint | Рендер и ручная правка соответствуют заявленному уровню поддержки |

Автоматические checks покрывают измеримые дефекты. Эстетику и ясность оценивает визуальный reviewer; общий процент сходства или отсутствие ошибок не подменяют эту оценку. После первых эталонов удачные правила фиксируются в shared modules и общих инструкциях, затем используются следующими diagrams.
